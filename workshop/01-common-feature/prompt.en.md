# Common Prompt — Saved Resources

Copy the following prompt into Kiro.

---

Create a new feature spec called `saved-resources-foundation`.

Before creating the Spec:

1. Read the relevant `.kiro/steering` files.
2. Inspect the current repository implementation.
3. Do not assume architecture, behavior, or dependencies that do not currently exist.

Pay particular attention to:

- the current authenticated workspace;
- the existing Cognito/OIDC authentication flow;
- how the access token is used for protected requests;
- the API Gateway JWT Authorizer;
- the existing `GET /hello` integration;
- the current OpenAPI contract;
- `apps/api` as the backend application workspace;
- the existing CDK infrastructure and stack boundaries;
- current frontend, styling, and testing patterns;
- existing scripts and configuration when relevant.

## Context

This repository is an already functioning AWS starter.

It currently includes:

- React + TypeScript frontend;
- Amazon Cognito Managed Login;
- OAuth 2.0 Authorization Code Flow + PKCE;
- API Gateway HTTP API;
- Cognito JWT Authorizer;
- AWS Lambda;
- CloudFront + private S3;
- AWS CDK;
- a protected `GET /hello` endpoint.

The goal is to evolve the existing system, not rebuild it or replace its accepted architecture.

## Goal

Allow an authenticated user to save useful resources and retrieve only the resources that belong to them.

A saved resource must contain:

- `resourceId`, generated by the backend;
- `title`;
- `url`;
- `createdAt`, generated by the backend.

Ownership must be derived by the backend from the validated Cognito identity.

Never accept an authoritative `ownerUserId` sent by the frontend.

## MVP Scope

Implement the first functional Saved Resources vertical slice.

The API must support:

```http
POST /resources
GET /resources
```

### POST /resources

It should receive only the information required to create the resource:

```json
{
  "title": "AWS Lambda Best Practices",
  "url": "https://docs.aws.amazon.com/"
}
```

The backend must generate:

- `resourceId`;
- `createdAt`;
- ownership from the validated JWT.

### GET /resources

It must return only the resources owned by the authenticated user.

It must not allow one user to retrieve another user's resources.

## Persistence

Use Amazon DynamoDB for persistence.

Design the simplest access pattern that satisfies the required behavior.

Do not add indexes, additional tables, or modeling complexity without a concrete need.

## Backend

Application logic should live in the existing backend workspace, normally under `apps/api`, following current repository conventions.

Do not implement business logic as inline code inside CDK.

Infrastructure should define infrastructure.

Application code should contain business behavior.

## Authorization and Security

Preserve the current authentication boundary:

```text
React
→ Cognito Managed Login
→ Authorization Code + PKCE
→ API Gateway JWT Authorizer
→ Lambda
```

Do not implement custom authentication.

Do not add password forms inside React.

Do not trust ownership supplied by the client.

The backend must derive the user identifier from validated JWT claims.

## Validation

At minimum:

- `title` cannot be empty after trimming;
- `url` must be a valid `http` or `https` URL;
- `resourceId` must be generated server-side;
- `createdAt` must be generated server-side;
- ownership must be derived server-side;
- one user must never receive another user's resources.

Define clear, consistent errors for invalid input and expected failures.

## Frontend

Integrate Saved Resources into the existing authenticated workspace.

Preserve:

- the current header;
- user menu;
- logout;
- existing authentication experience;
- the current protected `/hello` API status experience.

Evolve the main workspace area to include Saved Resources.

The user must be able to:

- see a loading state;
- see an empty state when they have no resources;
- create a resource using title and URL;
- see the new resource after creation;
- view existing resources;
- receive clear feedback if an operation fails.

Reuse existing components, styles, tokens, and visual patterns.

Do not add a sidebar or unnecessary navigation.

## OpenAPI

OpenAPI remains the source of truth for the API contract.

Update the contract to correctly represent:

- `POST /resources`;
- `GET /resources`;
- request schemas;
- response schemas;
- authentication;
- relevant errors.

Do not add endpoints outside the scope of this feature.

## Infrastructure

Use the existing AWS CDK architecture.

Add only the infrastructure required for this feature.

The solution will likely require:

- a DynamoDB table;
- minimum IAM permissions for the Lambda functions;
- protected API Gateway routes;
- integration of the required handlers.

Preserve simple, acyclic stack dependencies.

Do not introduce new AWS services without a concrete requirement.

## Testing

Include focused tests covering at least:

- resource creation;
- resource listing;
- backend validation;
- ownership isolation between users;
- frontend loading / empty / success / error states;
- regression of the existing authenticated workspace.

Reuse existing testing patterns in the repository.

## Out of Scope

Do not implement in this Spec:

- editing;
- deletion;
- categories;
- tags;
- search;
- filters;
- pagination;
- favorites;
- sharing;
- public resources;
- URL previews;
- metadata scraping;
- new authentication methods;
- new navigation modules;
- infrastructure not required by this vertical slice.

These capabilities may be explored in later challenges.

## Acceptance Criteria

The Spec must define verifiable criteria covering at least:

1. An authenticated user can create a resource with title and URL.
2. `resourceId` and `createdAt` are generated by the backend.
3. Ownership is derived from the validated JWT, not from the client request.
4. `GET /resources` returns only resources owned by the authenticated user.
5. Resources persist in DynamoDB.
6. The UI provides appropriate loading, empty, success, and error states.
7. A newly created resource becomes visible to the user without manual data manipulation.
8. Invalid inputs produce clear errors.
9. OpenAPI reflects the implemented contract.
10. Required infrastructure is defined with CDK.
11. IAM permissions follow reasonable least privilege.
12. Existing Cognito and `/hello` behavior continues to work.
13. No capabilities outside the MVP scope are introduced.
